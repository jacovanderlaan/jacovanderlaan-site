Concepts

A named vocabulary.

Model-Driven Data Engineering earns its own words. These are the coined concepts behind the method — one memorable name per idea, so a team can point at it, reuse it, and build on it. A shared language for business, engineers and AI.

Umbrella thesis

Model-Driven Data Engineering
Building scalable, metadata-driven data platforms from models — not hand-written code.

The master brand: an approach where the data platform is generated from models and metadata rather than written and maintained by hand. Models are the source of truth; SQL, tests, lineage and documentation are derived from them deterministically.

Signature principle

Structure Beats Magic
Output quality comes from the structure around the tools, not the tools themselves.

The first principle: results are produced by deliberate structure — models, rules, metadata, patterns — not by clever prompts or hope. The same thesis that anchors the SBM personal brand, applied to enterprise data.

Business-Friendly family

Business-Friendly Mapping
Data mappings written so business people can read, review and trust them.

Making the transformation logic between source and target legible to the business — mappings expressed as reviewable, metadata-driven statements of intent instead of opaque code.

Business-Friendly Diagramming
Clear, consistent, metadata-driven diagrams that connect business and technology.

The art and practice of generating diagrams from metadata so they are always correct, consistent and readable by both business and technical audiences.

Business-Friendly Metadata
Metadata explained and governed so it makes sense to both business and technical audiences.

Bridging data engineering and business understanding — metadata, lineage, data contracts, mappings and models explained, governed and applied so both sides understand them.

Business-Friendly Data Lineage
Data lineage made clear and actionable for decision makers.

Lineage rendered for humans who make decisions — not just a technical dependency graph, but an explanation of where data comes from and what it means.

Business-Friendly Data Mapping
Bridging technical data models and the people who need to use them.

Modern platforms are full of complex metadata, lineage and technical detail. Business leaders need clarity, not code — this is the practice of delivering it.

Business-Friendly Data Modeling
Making data models clear and valuable for the business.

Models designed and presented so the business can see its own concepts in them and derive value, rather than treating the model as a purely technical artefact.

Collaborative Data Modeling
Business and engineers model together in real time — the model as a shared conversation.

Modeling as a shared, live activity rather than a handover: business experts and engineers build the model together, using business-friendly notation and diagrams generated from metadata, so the model is a conversation both sides own — not a technical artefact thrown over the wall.

Architecture

Business-Shaped Integration Layer
An integration layer whose structure follows business domains, not source-system topology.

An integration architecture organised around business entities and domains — the shape of the business, not the accident of which source systems happen to exist.

Anti-Corruption Layer
A boundary that keeps a clean model from being polluted by messy upstream sources.

A translation boundary (borrowed from DDD, owned here for data platforms) that isolates a clean, governed model from the quirks and corruption of upstream source systems.

SQL & generation

SQL-First Modeling
Model in SQL — the language the platform already runs — rather than a separate modeling tool.

Treating SQL itself as the modeling surface: the model lives close to the engine that executes it, avoiding a translation gap between a modeling tool and the running platform.

Deterministic SQL Generation
Identical, repeatable SQL from the same metadata — a hard invariant.

Generating SQL that is byte-for-byte reproducible: no non-deterministic functions, no sorting ambiguity, no random tie-breaks. A hard invariant, not a nice-to-have.

Self-Describing SQL
SQL that carries its own meaning — metadata embedded where the query lives.

SQL files that describe themselves: structured metadata embedded as part of the file so the query explains its own schema, intent and lineage.

Atomic SQL
Each SQL file is self-contained — it carries its own metadata and runs independently.

A pattern where every SQL file is self-contained with all metadata embedded as structured comments — executable on its own, yet deployable into any metadata platform.

Model Close to the Data
Metadata, validation and governance live where the data lives — where the SQL runs.

The architectural principle that rules and metadata should sit next to the data and the engine, not in a separate governance system that drifts out of sync.

CTE Regression Testing
Compare a migrated query CTE-by-CTE to find the exact step that changed.

Automated CTE-by-CTE comparison of query results before and after a migration — finding the root-cause difference instead of only comparing final output.

Metadata OS

Metadata Operating System
Metadata as the operational centre — governing models, lineage, contracts and execution.

A vision where metadata is not documentation on the side but the operating system of the platform: it governs models, lineage, contracts and execution.

Universal Metadata Models
A reusable, universal way to structure metadata for models and mappings.

A shared, reusable schema for metadata itself — so models, mappings and platforms describe themselves in one consistent way.

Universal Data Models
Reusable patterns for clear, scalable data models.

A catalogue of reusable modeling patterns that make data models consistent and scalable across projects and domains.

Data Capsule
Data shipped together with its complete metadata as one versioned, executable unit.

A single, versioned, executable unit where data ships with its full metadata — schema, properties, quality, contracts, classification and lineage — in one place.

Capsule Slot
One of the six conventional metadata containers inside a Data Capsule.

The six conventional slots of a capsule — schema, properties, quality, contracts, classification, lineage — each a well-known place for one kind of metadata.

Completeness Gate
A CI gate that requires specific metadata slots before a deployment is allowed.

A CI enforcement mechanism that stages capsule adoption: it requires named metadata slots to be present before allowing a deployment, tightening strictness phase by phase.

Sidecar Tables
Companion metadata tables that live beside data assets without changing them.

Companion tables in the same schema and dataset that carry lineage, quality checks and masking rules alongside the primary data — metadata that travels with the asset.

Common Integration Layer
A governed semantic handshake between domains and systems.

A harmonised, governed representation of business entities and relationships that acts as the shared handshake between domains and systems.

Metadata Mesh
Federated, domain-owned metadata that still interoperates through shared standards.

Data Mesh's decentralisation applied to metadata: each domain owns and publishes its own metadata as a product, while shared standards and a common model let it interoperate across the enterprise — federation without fragmentation.

Metadata as Code
Metadata lives in version-controlled files — reviewed, tested and deployed like code.

Treating metadata as a first-class code artefact: definitions, contracts and models live in version control, get pull-request review, run through CI, and deploy like any other code — no more metadata trapped in a GUI or a wiki.

Lineage & governance

Semantic Drift
The slow loss of meaning when definitions and business intent aren't actively governed.

The gradual erosion of meaning in data when definitions, classifications and business intent are left ungoverned — combated with metadata-driven, text-first modeling.

Living Documentation
Documentation derived from metadata and lineage — so it never goes stale.

Documentation generated directly from the operational model, metadata and lineage — it evolves with the platform instead of rotting in a wiki.

Lineage Explorer
An interactive map of concepts, mappings, assets and releases.

An explorable graph that connects concepts, mappings, data assets and releases into one interactive map of how data flows and depends.

Horizontal vs Vertical Lineage
Left-to-right flow vs top-to-bottom drill-down.

Two axes of lineage: horizontal traces data flow from sources to targets; vertical traces drill-down within a single asset, from column to table.

Technical vs Functional Lineage
Code-level operations vs business meaning.

Two lenses on lineage: technical lineage shows joins and filters at code level; functional lineage shows business meaning and intent — why code-based lineage alone isn't enough.

Rulebooks, Playbooks, and Cookbooks
Three levels of metadata-driven governance: enforce, procedure, pattern.

Three tiers of governance shaped by metadata: Rulebooks (automated enforcement), Playbooks (procedural steps) and Cookbooks (technical implementation patterns).

Data Breadcrumbs
Trace markers left in the data itself, so any row can tell you where it came from.

Lineage carried in-band: every row (or asset) leaves a trail of markers — source, run, transformation, timestamp — so you can walk back from any value to its origin without a separate lineage system. Lineage you can follow from the data itself.

Model-Driven Data Quality
Automating data-quality checks with models, metadata and patterns.

Data-quality checks generated and driven by the model and its metadata rather than hand-written per table.

Architecture (anti-pattern)

Ivory Tower Architecture
The anti-pattern: architecture designed in isolation, disconnected from delivery.

The failure mode where architecture is designed in an ivory tower — elegant on paper, disconnected from how data is actually delivered and used. MDDE's foil.

Temporal patterns

Dual SCD2
Two coordinated SCD2 timelines for robust, deterministic history.

A historization design using two coordinated SCD2 layers, enabling deterministic integration and fast, reproducible as-of history.

Timeline Compression
Collapse overlapping SCD2 records with identical values into one.

A temporal optimisation that consolidates overlapping SCD2 records carrying identical attribute values into a single record, reducing query complexity.

Bi-Temporal SCD2 with Redelivery Support
Track when data was true and when we recorded it — and reprocess corrections.

A historization pattern handling both valid-time and system-time, plus the ability to reprocess late-arriving corrections without losing history.

PIT Helper Tables
Pre-joined point-in-time tables that make 'as-of' queries fast.

Pre-joined point-in-time tables that accelerate 'as-of X' queries on dual SCD2 models, giving fast, reproducible access to history.

Exposure Views
A view layer that delivers clean, consumer-ready data from SCD2.

A layer of views over dual SCD2 tables that hides temporal complexity and delivers clean, consumer-ready data to BI and reporting.

Delivery & method

Model-Driven Data Delivery
Where models meet delivery — plan, manage and measure a common data platform.

Using models and metadata to plan, manage and measure the evolution of a shared data platform — the point where modeling meets delivery.

Model-Driven Data Architecture
Bridging models, metadata and meaning across the enterprise.

An architecture practice where models and metadata carry meaning across the enterprise, connecting design to running systems.

Model-Driven Agile Delivery
Where models guide the flow of work.

Letting models drive the flow of agile delivery — the backlog and the platform stay in step because both derive from the model.

Model-Driven Migrations
Plan and execute controlled platform migrations using metadata and automation.

Controlled migration of data platforms, modeling styles and sources driven by metadata and automation rather than manual rewrites.

Cooking with Data
Treat mappings as recipes — clear, repeatable, business-readable transformation steps.

Making ETL transformations clear and repeatable by treating mappings as recipes: transparent, business-friendly, step-by-step.

Shift-Left
Move quality, validation and schema enforcement earlier — to development time.

Moving quality, validation and schema enforcement earlier in the pipeline — from deployment gates back to development time.

Batteries Included
Metadata and governance ship with the platform, pre-configured.

A design philosophy where the metadata and governance infrastructure ships with the data platform itself — pre-configured and ready to deploy.

Transfer-by-Design
Knowledge lives in the team from day one — by design, not by handover.

An engagement principle: knowledge is transferred through deliberate pattern selection and shared documentation from day one, never via a late handover.

Cost-Friendly Data Architecture
Designing efficient, transparent, sustainable data platforms.

Architecture that treats cost as a first-class design concern — efficient, transparent and sustainable platforms.

How AI and generative tech are transforming data-model design.

Exploring how AI and generative technologies change the way we design, maintain and evolve data models — for architects who want to stay ahead.

A named historical break — around 2013 — when modular, composable templates were replaced by monolithic code generation, losing composability and maintainability.

AI & innovation (anti-pattern)

Vibe-Driven AI
The anti-pattern: AI steps that are non-deterministic, unspecified and ungated.

The failure mode where AI is dropped into pipelines with no specification, no determinism and no gate — reliable only by hope. The foil to Model-Driven AI.

Method

Architectural Decision Records
Big architecture choices written down with options and reasoning.

ADRs: durable records of architecture decisions capturing the context, the options considered and the reasoning — so the 'why' survives the people.

Contract-Driven Data Engineering
Data contracts are the source of truth — the platform is built to satisfy them.

An approach where explicit data contracts (schema, semantics, quality, SLAs) come first and the pipeline is generated and validated to satisfy them — producers and consumers agree on the contract, and the platform enforces it. A sibling paradigm to Model-Driven Data Engineering.

Semantic Data Engineering
Engineer the meaning, not just the movement — pipelines that carry business semantics.

Engineering pipelines around the meaning of data, not only its movement: business semantics, definitions and relationships are first-class metadata that travel with the data and drive generation, validation and lineage. The counter to plumbing-only data engineering.

Semantic DevOps
CI/CD for meaning — semantics and metadata versioned, tested and deployed like software.

The DevOps discipline applied to semantics: definitions, models and contracts flow through the same version-control, review, automated-test and deploy pipeline as code, with semantic changes gated and validated. Meaning ships on a release train, not by hand. Pairs Metadata as Code with the Completeness Gate.
